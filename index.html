Reading Documents out of Weight Updates: Hypernetwork-Written LoRA Adapters Linearly Encode Their Document

Aryan Keluskar, School of Computing and AI, Arizona State University

Paper PDF BibTeX

TL;DRHypernetwork-written LoRA adapters linearly encode their document, so a linear probe on the weight update recalls it while AdamW adapters can't. Noise can't hide it without breaking the adapter.

Abstract

Hypernetworks such as Doc-to-LoRA write an entire document into a low-rank weight update in a single forward pass. We ask whether the document can be read back out, and find that it can, but only when a hypernetwork wrote it. A linear probe from the low-rank factors of a Doc-to-LoRA update to the document’s bag-of-words identifies the held-out document at recall@5 = 0.86–0.99 across three model families (chance < 0.16), whereas ordinary SGD adapters that internalise the same documents are decodable only at chance, a 10–20σ gap at matched effective update norm. Mechanistically, an amortised update is a near-linear image of the document embedding (R² = 0.97) emitted from a low-dimensional subspace, whereas an SGD update is not a function of any shared embedding. The leak does not even require the weights: an attacker who can only query a deployed adapter recovers its document from output logits alone (recall@5 0.94, and 0.50 when the API exposes only its top-20 logprobs), and this behavioural leak is universal: even an SGD adapter, unreadable from its weights, regurgitates its document when queried (0.59). The readability of a weight update thus depends on its generator, and any deployed document fine-tune leaks its training text to whoever can query it.

Keywords: LoRA adapters, hypernetworks, weight-space interpretability, training data extraction. Published on OpenReview on August 4, 2026, under CC BY 4.0.

Can a weight update be read back?

The broad interpretability question is whether any weight update can be reversed into its inputs. Two practical reasons to care:

  • Auditing. Was my copyrighted document trained into this adapter?
  • Privacy. Is my sensitive information inside a LoRA adapter?

The strongest attack would reconstruct the text. That has been done from embeddings (Morris et al., 2023), from model outputs and from gradients, but from weights it is still open. This paper takes the first step: identify which document an adapter was trained on.

Two ways to write a document into weights

A hypernetwork is a network that outputs the weights of another network (Ha et al., 2017). Doc-to-LoRA (Charakorn et al., 2026) converts a raw document into ΔW in one forward pass, and adding ΔW gives the base model the document as context. Its authors released checkpoints for three base models, and the paper uses all three. The comparison is ordinary fine-tuning with AdamW.

Three questions

  1. Can a linear probe identify the document from an adapter’s weights, and does that depend on how the adapter was written?
  2. Why is a hypernetwork update readable when an AdamW update of the same document isn’t?
  3. How can you identify the document behind a publicly released adapter, and can noise hide it?

Identification means: given an adapter and N candidate documents, find the one it was trained on. The tool is the oldest one in interpretability, a linear probe (Alain & Bengio, 2017), pointed at the weight update instead of at activations. Random projections shrink ΔW, and the probe predicts the document’s words. The metric is recall@5, the share of held-out adapters whose true document ranks in the top 5.

RQ1A probe reads hypernetwork adapters, not AdamW ones

On all three base models, the probe finds the true document in its top 5 for 86–99% of hypernetwork-written adapters. AdamW adapters learned the same documents, yet they are near random to identify.

The probe never sees the text, yet its top predicted words name the document. Against a word-frequency baseline, its precision@10 is 0.45 versus 0.15.

It isn’t size, capacity or the objective

Update norms are similar, 6.7 for the hypernetwork and 5.9 for AdamW. Giving AdamW rank 32, every MLP module, or a context-distillation objective leaves it at 0.17–0.19. And it isn’t one particular hypernetwork: a hypernetwork trained from scratch for this paper and Text-to-LoRA (Charakorn et al., ICML 2025), which writes the attention q_proj, are both decodable. Readability depends on how the update was written.

RQ2Why hypernetwork updates are readable

A hypernetwork is a smooth map from a document embedding to the update. Its updates lie on a low-dimensional subspace, while AdamW updates fill many directions. A linear fit from the document embedding to the update shows the difference:

R² 0.97for the hypernetwork trained for this paper
R² < 0for AdamW, worse than predicting the mean

Keeping only the top k principal directions of the update makes the same point. With 8 directions, hypernetwork adapters still reach 0.54 recall@5 and AdamW adapters 0.10. The hypernetwork writes the document into a few shared directions.

Which layers hold the document

Early layers reach about 0.87 recall@5 and late layers about 0.8, while middle layers manage about 0.4. A single early layer does about as well as all layers pooled.

RQ3Auditing a released adapter

The threat model: someone releases an adapter, the hypernetwork that wrote it is public, and you hold 320 candidate documents. Use the public hypernetwork to mint your own (document, ΔW) pairs, train the probe on them, and rank the candidates for the released adapter. The metric is AUC, the chance that the true document ranks above a random wrong one.

With 1,200 candidate documents, recall@5 falls to 0.32 but AUC stays at 0.98. For privacy, the probe’s top 20 words recover a third of the document’s named entities and numbers, 0.32 against a 0.10 baseline. Anyone with the public hypernetwork can check which document an adapter holds.

The paper’s abstract adds that the weights aren’t even needed. An attacker who can only query a deployed adapter recovers its document from output logits alone, at recall@5 0.94, or 0.50 when the API exposes only its top-20 logprobs. Even an adapter trained by gradient descent, unreadable from its weights, regurgitates its document when queried (0.59).

Can noise hide the document?

One defense is to add Gaussian noise to the adapter before releasing it, so the probe fails while the adapter still works. It doesn’t get there.

Summary

  1. A linear probe identifies the document when a hypernetwork wrote the adapter, on all three base models.
  2. For the hypernetwork trained here, the update is close to a linear function of the document embedding.
  3. Training the probe on pairs from the public hypernetwork identifies the document behind a released adapter (AUC 0.96), and noise can’t hide it without breaking the adapter.

So there is now a way to test whether a hypernetwork-written adapter holds your copyrighted or sensitive documents.

Open directions

  • A defense that hides the document without breaking the adapter
  • More privacy tests for training-data identification
  • An index of adapters, to fetch the one that holds a given document
  • How release-time changes such as lower rank or quantization affect readability
  • Reconstructing the document’s text, not just identifying it
